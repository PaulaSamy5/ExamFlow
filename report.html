1. نظرة عامة على المشروع (Project Overview)

تعد منصة ExamFlow حلاً متكاملاً ومبتكراً لإعداد وإدارة وتصحيح الامتحانات الأكاديمية بنوعيها: الإلكتروني (Online Exams) والورقي القابل للطباعة (Printable Exams). تتميز المنصة بدمج قدرات تقييم ذكاء اصطناعي محلي ومجاني تماماً لمساعدة الأساتذة في تسريع عملية التصحيح دون تحمل تكاليف اشتراكات أو استهلاك واجهات برمجة تطبيقات (APIs) مدفوعة.

الميزات الرئيسية للمنصة:

  • التصحيح التلقائي لرسومات UML: تصحيح فوري لمخططات حالات الاستخدام (Usecase)، الفئات (Class)، العلاقات الكينونية (ERD)، النشاط (Activity)، والتتابع (Sequence) باستخدام معالجة الصور ومقارنتها بالنموذج الإرشادي للمعلم.
  • التقييم المقالي الذكي (Essay AI): تحليل الإجابات المقالية ومطابقتها دلالياً ومفاهيمياً مع الإجابة النموذجية مع مراعاة المترادفات وصياغات الجمل المختلفة دون كلفة مالية.
  • تصحيح الرياضيات بالخطوات: نظام لتقييم حلول المسائل الرياضية بناءً على الناتج النهائي بالإضافة إلى خطوات الحل المحددة من قبل المعلم.
  • الامتحانات القابلة للطباعة: إعداد وتنسيق الامتحانات الورقية بشكل احترافي مع إمكانية إدخال بيانات المؤسسة، القسم، واللوجو الخاص بالجامعة.

الأدوار المدعومة في النظام (User Roles):

المسؤول (Admin)

التحكم الكامل بالنظام، إدارة حسابات المعلمين والطلاب، وضمان توافر النظام وصيانته.

المعلم (Instructor)

إنشاء الامتحانات، ورفع حلول UML والرياضيات النموذجية، ومراجعة تصحيحات الـ AI واعتماد الدرجات النهائية.

الطالب (Student)

أداء الاختبارات الإلكترونية، ورفع ملفات الحلول والمخططات، واستعراض الإحصائيات الفردية والدرجات.

2. البنية التقنية والبنية التحتية الحالية

تم تصميم منصة ExamFlow باتباع معايير الويب الحديثة لضمان سرعة التحميل وتجربة مستخدم متميزة. البنية مقسمة بالكامل لضمان فصل المهام وتسهيل التطوير المستقبلي.

البنية التقنية (Tech Stack):

المكون التقنية المستخدمة الوظيفة الحالية
الواجهة الأمامية (Frontend) React.js / Vite / Vanilla CSS بناء صفحات الويب التفاعلية، أداء الاختبارات للطلاب، وإعداد الامتحانات للمدرسين.
الواجهة الخلفية (Backend) Node.js / Express.js إدارة المنطق البرمجي، التحكم بالصلاحيات والمستخدمين، معالجة طلبات قاعدة البيانات.
خادم الذكاء الاصطناعي Python / FastAPI تصحيح مخططات UML باستخدام OpenCV ومقارنة النصوص دلالياً بالاعتماد على خوارزميات محلية.
قاعدة البيانات PostgreSQL (Neon) تخزين الحسابات، الامتحانات، حلول الطلاب، والدرجات بشكل فوري وآمن.
خدمة البريد الإلكتروني Brevo HTTP API إرسال كود التحقق (OTP) لحسابات المستخدمين الجدد واستعادة كلمات المرور عبر طلبات HTTPS آمنة.

البنية التحتية الحالية وموقع الاستضافة:

  • استضافة الواجهة الأمامية: مستضافة على منصة Vercel بفضل ربطها المباشر بمستودع كود المشروع على GitHub للتحديث التلقائي.
  • استضافة السيرفر والذكاء الاصطناعي: مستضافة على منصة Railway Cloud كخدمتين منفصلتين (واحدة لـ Node.js وأخرى لـ FastAPI) لضمان عدم تأثير العمليات الحسابية الثقيلة للـ AI على سيرفر النظام الرئيسي.
  • التحقق والأمان: تتم المصادقة باستخدام رمز JWT (JSON Web Token) المخزن محلياً بالمتصفح لحماية الجلسات، مع دعم التفعيل الآمن للحسابات برمز OTP يتم توليده بشكل عشوائي عند التسجيل.
  • تخزين الصور والملفات: لا تستعين المنصة حالياً بخدمة تخزين ملفات سحابية خارجية (مثل AWS S3). بدلاً من ذلك، يتم تحويل الصور المرفوعة من الطلاب ومخططات الحلول النموذجية إلى نصوص مشفرة بصيغة Base64 ويتم حفظها مباشرة داخل جداول قاعدة بيانات PostgreSQL.

3. حدود وسعة البنية التحتية الحالية (Limits & Capacity)

المنصة تعمل حالياً على باقات استضافة وقواعد بيانات مجانية/مشاركة. يوضح الجدول التالي السعة التشغيلية والحدود المسموح بها في البيئة الحالية:

قاعدة بيانات Neon (PostgreSQL)
الحد الأقصى للمساحة: 512 ميجابايت (0.5 GB)

نظراً لأن صور UML تُحفظ بصيغة Base64 مباشرة بالـ DB، فإن هذا الحجم يعتبر محدوداً جداً. مع تفعيل الاختبارات المليئة بالرسومات، قد تمتلئ قاعدة البيانات بعد حوالي 1000 إلى 2000 تسليم فقط. (يجب ترقية الباقة لاحقاً أو فصل تخزين الصور).

إرسال البريد الإلكتروني (Brevo)
الحد اليومي: 300 رسالة يومياً

الخطة المجانية لـ Brevo تسمح فقط بإرسال 300 إيميل يومياً. هذا يعني أن إجمالي عدد عمليات التسجيل الجديدة، استعادة كلمات المرور، أو أي إشعارات إيميل أخرى لا يمكن أن تتجاوز 300 طلب يومياً لجميع مستخدمي المنصة.

موارد الخوادم (Railway Cloud)
الذاكرة المتاحة: 512 ميجابايت (RAM) لكل خدمة

سيرفرات Railway المشتركة تضع حداً أقصى للذاكرة يبلغ 512MB. هذا كافٍ تماماً لخادم backend الـ Node.js، ولكنه يمثل حداً حرجاً لخادم Python المسؤول عن معالجة الصور ومقارنتها عبر OpenCV عند الاستخدام الكثيف.

القدرة الاستيعابية المتزامنة
50 - 100 مستخدم نشط في نفس الوقت

قاعدة بيانات Neon المجانية تحدد عدد الاتصالات المتزامنة (Database Connections) بـ 10 اتصالات فقط. وبناءً على ذلك، يمكن للمنصة دعم ما بين 50 إلى 100 مستخدم يتصفحون ويؤدون الاختبارات في نفس اللحظة بدون مشاكل بطء.

4. كيفية مراقبة الاستخدام ومتابعة المشاكل

لمتابعة سير عمل المنصة وضمان عدم تجاوز حدود الخدمات المجانية، يمكن للمسؤولين متابعة الاستهلاك والمشاكل من خلال لوحات التحكم الرسمية للمزودين:

لوحة Neon DB

مراقبة مساحة تخزين قاعدة البيانات

من خلال الدخول لحساب Neon (neon.tech) والاطلاع على تبويب Storage لمراقبة الاستهلاك الفعلي للمساحة بالـ Megabytes للتأكد من عدم الاقتراب من حد الـ 512MB.

لوحة Railway

مراقبة استهلاك المعالج والذاكرة وسجلات السيرفر

من لوحة تحكم مشروعك في Railway، اضغطي على خِدمة الـ backend أو الـ AI وافتحي تبويب Metrics لرؤية استهلاك الذاكرة والـ CPU، وتبويب Deploy Logs لمتابعة أي أخطاء برمجية أو رسائل سقوط خوادم مباشرة.

لوحة Vercel

مراقبة سرعة الواجهة وحجم الباندويث

عبر الدخول لمشروعك في Vercel ومراقبة تبويب Analytics و Usage لمتابعة عدد زيارات الموقع وحجم الباندويث المستهلك (من أصل الـ 100GB).

لوحة Brevo

متابعة حصة رسائل البريد اليومية

عبر لوحة Brevo الرئيسية لمشاهدة كم إيميل متبقي للنظام اليوم، والاطلاع على التقارير لمعرفة ما إذا كانت هناك إيميلات تم رفضها أو تعليقها من قِبل مزودي البريد مثل Google أو Outlook.

5. نقاط الضعف الحالية والتوصيات المستقبلية

تم بناء المشروع بشكل متين ومناسب جداً للنسخة الحالية، ولكن لضمان جاهزية المنصة للاستخدام الفعلي على مستوى كليات أو جامعات، يجب الأخذ بعين الاعتبار النقاط التالية:

⚠️ مشكلة حفظ الصور بالـ Base64 في قاعدة البيانات

الوضع الحالي: يُسبب تضخماً هائلاً وسريعاً في حجم قاعدة البيانات، مما يهدد بالوصول لحد Neon المجاني (512MB) مبكراً جداً.
التوصية الفنية: الانتقال لتخزين الصور والملفات المرفوعة على سيرفر تخزين خارجي (مثل Cloudinary أو AWS S3) وحفظ الروابط فقط في قاعدة البيانات. هذا يقلل استهلاك قاعدة البيانات بنسبة 95%.

⚠️ عنق الزجاجة في خادم الذكاء الاصطناعي (AI Bottleneck)

الوضع الحالي: معالجة الصور الرياضية والهيكلية (OpenCV) تتم بالكامل على معالج السيرفر المشترك بذاكرة 512MB. إذا قام عدد كبير من الطلاب بالضغط على زر "تسليم مخطط UML" في نفس اللحظة، فقد يتوقف الخادم بسبب نقص الذاكرة (Out of Memory).
التوصية الفنية: تحويل عملية التصحيح إلى طابور خلفي (Background Queue) بحيث يسلّم الطالب إجابته ويقوم السيرفر بالتصحيح بالتدريج خلف الكواليس لتجنب سقوط الخادم.

⚠️ غياب النسخ الاحتياطي التلقائي (Auto-Backups)

الوضع الحالي: لا توجد عملية نسخ احتياطي مجدولة خارج بيئة Neon DB لبيانات الطلاب والاختبارات.
التوصية الفنية: تفعيل النسخ الاحتياطي التلقائي اليومي لقاعدة البيانات وتخزينه في مكان آمن لضمان عدم ضياع درجات الطلاب في حال حدوث أي خلل.

🚀 ميزات مستقبلية مقترحة:

  • ربط نماذج لغوية ذكية (LLMs): دمج نماذج ذكاء اصطناعي (مثل Llama 3 أو GPT) لتوفير تقييم مقالي أكثر مرونة ودقة وتوفير تبريرات ذكية للدرجة للطالب.
  • نظام مراقبة الامتحانات (Proctoring System): إضافة ميزات أمنية إضافية مثل منع فتح تبويبات جديدة بالكامل أو كشف الغش أثناء الاختبارات الإلكترونية بشكل أفضل.

6. تقييم جاهزية الإطلاق الفعلي (Production Readiness)

مستوى الجاهزية الحالي لكل مكون من مكونات النظام مقيم بالنسبة المئوية ومصحوباً بتبرير تقني للدرجة:

نظام المصادقة والأمان (Authentication) 90% (ممتاز)

نظام المصادقة يعتمد بالكامل على JWT مشفرة، وتم حل مشكلة إزاحة المنطقة الزمنية (Timezone Drift) لرموز الـ OTP تماماً لضمان عدم انتهاء صلاحيتها بشكل خاطئ.

قاعدة البيانات وعلاقاتها (Database) 80% (جاهز للتشغيل)

قواعد البيانات PostgreSQL المدارة بواسطة Neon ممتازة وسريعة، والجدوال مهيأة بالكامل، والحد الوحيد المقلق هو المساحة التخزينية المخصصة للـ Base64 للصور المرفوعة.

خادم التصحيح بالذكاء الاصطناعي (AI Core) 70% (مقبول - يحتاج رقابة)

محرك التصحيح يعمل محلياً بالكامل ومجاني تماماً، وهي ميزة تنافسية ممتازة. لكنه قد يتباطأ تحت الضغط العالي بسبب استهلاك الرام لمعالجة الصور. كما يعتمد على دقة رفع الطلاب للصور.

إعدادات النشر والاستضافة (Deployment) 90% (ممتاز)

توزيع الخدمات (Vercel للـ frontend و Railway للـ API والـ AI) تم بشكل ممتاز ومستقر للغاية مع ربط آمن. وتم تهيئة الـ CORS لقبول جميع استضافات Vercel لضمان عمل واجهات المعاينة الفورية بسلاسة.

الأداء والاستجابة (Performance) 70% (مقبول)

السرعة فائقة للمستخدمين الفرديين، ولكن نظراً للخطط المجانية المتاحة للمشروع حالياً، قد يتباطأ أداء النظام خلال فترات الامتحانات الكبيرة (أكثر من 100 طالب يؤدون الامتحان في نفس اللحظة).
